# Cleany — 제품 맥락과 하드웨어

기준일: 2026-10-09. 로봇 구현 브랜치 `feat/runtime-integration`, 소스 기준 `c082d1d`, KB commit `9931007`. 초기 문서 기준 `16504ee`에 runtime cleanup 6개 커밋과 Nav2 BT 추적·설정형 기록 기능을 통합했다. 10/09 accuracy review·SCRUM-426 도구·ROS 그래프 개선·navigation 회귀 도구·공유 voxel 변경도 통합했다. 기존 주행 기록과 이번 통합 검사를 구분한다.

## 사용자 문제와 기대 가치

Cleany(끌리니)는 무인 스터디카페 운영자가 이용자 퇴실 뒤 책상에 남은 물체를 직접 확인하고 처리하는 부담을 줄이려는 모바일 매니퓰레이터 프로젝트다. 쓰레기와 개인 소지품 가능성이 있는 물체를 구분하고, 처리 전후 상태·미처리·실패를 원격에서 확인하는 것이 목적이다.

이 문제와 가치는 팀이 선택한 제품 가설이다. 읽은 KB에는 운영자 인터뷰나 현장 관찰로 검증한 결과가 없으므로 시장 검증이 끝났다고 말하지 않는다. 프로젝트는 AI·SW마에스트로 17기 팀 ‘AI 에이전트는 움직이고 싶어’의 Cleany다.

## 목표 MVP 시나리오

1. 운영자가 Dashboard에서 개별 좌석을 선택해 작업을 요청한다.
2. Backend가 요청을 대기열에 넣고 로봇에 미션을 제안한다.
3. 로봇이 사전 제작 지도와 좌석 접근 pose로 대상 책상에 이동한다.
4. 작업 전 RGB-D 장면과 여러 물체를 관찰한다.
5. Planner가 다음 고수준 행동 하나를 제안한다.
6. Mission Manager와 실행 계층이 허용된 대상·행동·물리 조건을 검사한다.
7. 쓰레기 후보를 집어 로봇 탑재 수거함에 넣고 장면을 재관찰한다. 남은 대상에 대해 판단→실행→관찰을 반복한다.
8. 작업 후 관찰을 남기고 대기 위치로 복귀한다.
9. Dashboard가 전후 자료, 처리·미처리 대상과 최종 결과를 표시한다.

이 흐름은 제품 목표다. 현재 통합 주행 시험에서 4~7의 실제 물체 처리는 mock이다.

## 포함·제외 범위

| 항목 | 기준 |
|---|---|
| 미션 단위 | 운영자가 지정한 개별 좌석의 책상 한 곳 |
| 이동 | 사전 제작 지도에서 대상 좌석과 대기 위치 사이 왕복 |
| 대상 | 여러 쓰레기 후보와 분실물 후보 |
| 쓰레기 | 정책과 집기 조건을 통과한 대상만 로봇 탑재 수거함으로 이동 |
| 분실물 | 인식 대상이지만 발견 이후 물리 행동과 인계 흐름은 미정 |
| 실패·불확실 | 결과에 남김. 정확한 사용자 흐름과 표현은 추가 결정 필요 |
| 시연 | 사람 없는 통제 구역, 작업 구역 밖 감독자와 비상 정지 수단 |

의자 정렬, 바닥 청소, 책상 닦기, 소등·문단속, 데모 중 새 지도 제작, 사람과 함께하는 자율 운영, 임의 자연어 행동 생성, 상용 다점포·다중 로봇 최적 배차·과금은 MVP 범위 밖이다.

특히 분실물을 별도 보관함으로 옮기는 행동은 현재 제품 기준으로 확정되지 않았다. 일부 오래된 구현 소개에 `store_lost_item` 등이 있어도 최신 KB의 미결정 정책을 대체하지 않는다.

## 성공 기준

| 단계 | 통과 의미 |
|---|---|
| Rule-based 통합 | 요청→이동→여러 물체 관찰→규칙 기반 제안→검증 가능한 조작→재관찰→복귀→전후 결과가 연결됨 |
| 목표 MVP | 위 경계에서 AI가 장면·순서를 제안하고 VLA를 포함한 물리 실행 결과를 새 관찰로 확인함 |
| 승인된 축소 데모 | 팀이 따로 승인한 축소 범위만 인정하고 시뮬레이션·영상 대체 및 미완료 단계를 명시함 |

KB는 물체별 성공률·반복 횟수의 고정 수치 목표를 아직 정하지 않았다. 최근 주행의 실측 RTF 2 목표는 특정 개발·검증 과제이며 전체 제품의 성공 기준과 동일하지 않다.

부품 목록·개념 이미지·시뮬레이터 CAD는 실제 조립 완료의 증거가 아니다. 완성 로봇의 현재 배선·장착·기구·e-stop 상태를 확인하는 실물 조립 기록은 이번에 읽지 않았다.

### 베이스의 실제 구현 계약

ROS driver가 `/cmd_vel`의 x/y/yaw를 wheel 목표로 바꾸고 micro-ROS Agent를 통해 MCU에 전달한다. MCU가 엔코더·PI+feed-forward·PWM을 처리하며 wheel feedback을 ROS로 반환한다.

실물 초기 profile의 휠 반경은 0.0635m, 앞뒤 휠 중심 간격은 0.350m, 좌우 휠 중심 간격은 0.610m다. 시뮬레이션 geometry와 구분한다. wire 배열은 FL/FR/RL/RR이고 PCB 모터 순서 변환은 MCU가 담당한다.

시작·통신 단절·재부팅 이후는 구동 비허가다. 명시적인 enable과 그 이후의 새 명령이 필요하며 이전 이동 목표를 복원하지 않는다. host 명령 timeout은 초기 설정 0.3초, MCU watchdog 상한은 250ms다. 이 값은 구현 설정이지 하중 조건에서 검증된 정지 거리나 바닥 주행 허가가 아니다.

## 결정의 이유

- 표준 XLeRobot의 3륜 omni 대신 4륜 Mecanum을 선택해 전후·좌우 이동과 회전을 같은 상위 속도 계약으로 다룬다. custom assembly·slip·odometry는 별도 검증 대상이다.
- AGX Orin 64GB에서 Orin NX 16GB로 변경한 이유는 당시 메모리·조달 비용이다. 모델 성능 검증을 대신한 선택은 아니다.
- 고수준 Planner와 물리 실행 Skill을 분리했다. VLM/API는 제안하고 Mission이 검증하며, VLA는 필요하면 Skill 내부에서 arm action을 생성한다.
- 별도 범용 `Local Guard` package를 MVP 필수 구조로 두지 않는다. 검증은 Mission·Capability·backend 책임으로 나눈다. 현재 주행의 collision/reactive/voxel guard는 별도 저수준 안전 기능이다.

## 현재 체크아웃의 의미

로봇 코드의 기준은 `feat/runtime-integration` 소스 commit `c082d1d`다. runtime cleanup 6개 커밋과 Nav2 BT 추적·설정형 기록 기능도 통합했다. facility·navigation-runtime·mission-runtime·dev-monitor의 커밋된 작업을 합친 통합 브랜치이며, 주행 성능·안전 관측·최종 도착 검사가 추가됐다. 원격 main 반영·현재 PR·배포 상태를 확인한 것은 아니다.

운영 Dashboard와 Backend는 별도 `cleany-control-plane` 저장소다. 이번에 경계를 확인한 상대 체크아웃은 `feat/robot-gateway` HEAD `0919d38`이며 다른 브랜치의 계정 기능·인증을 이 기준의 완료 상태로 포함하지 않았다. KB 기준은 submodule `9931007`이다.
